# Atomic campaign publication — 2026-10-28

The old publisher verified membership and registry ownership, then wrote the team draft and public registry using separate service-key upserts. Two tenant owners could both pass the first-ID preflight; the later unconditional registry upsert could replace the first tenant's ownership. A second-write failure could also leave only one record changed. Publishing could replace a teammate's newer saved draft without comparing its contents.

A rolled-back disposable SQL reproduction demonstrates the old upsert takeover with the new guard absent. The new migration adds a registry identity/owner guard, preserving the existing workspace-FK deletion behavior. A service-only RPC locks current membership, serializes the public campaign ID (including first creation), checks tenant ownership and the current saved team contents, then updates both records in one transaction. Membership removal/demotion is locked through commit. A changed/missing team draft must be deliberately saved and reviewed again; it is not overwritten by publication. Public registry versions and team draft versions remain separate.

Only the server role can call this RPC. The Edge handler still verifies the actual user JWT and owner/admin role; its actor argument comes from verified Auth, never request-body identity. The database repeats authorization under locks. A temporary transaction-local subject supplies that verified actor to existing draft audit triggers and is restored afterward, including on rollback. No browser can execute the actor-selecting function. This is not a new client-accessible impersonation facility.

The Edge handler now makes one publication RPC instead of separate data writes, returns fixed conflict/unavailable messages and never sends raw database errors to the browser. Non-array catalog input now returns a controlled 400 instead of reaching a throwing loop. The publisher's SDK import is pinned to 2.118.0, matching the verified npm SDK; other Edge functions retain their own dependency controls. Studio retains the exact returned draft revision/creation stamp so publishing or archiving does not itself cause a false conflict on the next edit. A wrong-incarnation acknowledgement cannot advance the editor's loaded revision.

## Installation and rollback boundaries

Review-only; no hosted SQL, server deployment or production change has occurred. The new migration and changed Edge handler are outside the founder's PR #24 staging approval. A future separately approved staging installation must first retain the existing canonical Workspace dependency order, then apply workspace-draft-revisions.sql and campaign-publication.sql before using the new publisher.
