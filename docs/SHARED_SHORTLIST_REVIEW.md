# Persistent Together shortlist → private plan

A confirmed pair can open a shared shortlist from Friends, consider fair ranked catalog suggestions or add a specific title/link, and independently express interest or pass. Each person can choose one active idea. Only two independent choices of the same immutable suggestion can create a plan proposal. The server creates one plan with mutual interest and no schedule approvals; existing Plans then requires both accounts to approve the same date/place revision. Changing details still resets approvals. Existing private calendar export remains explicit and is not a booking.

Users can explicitly suggest a planned idea again. This creates a fresh option with no copied responses, choices, schedule or approvals; it cannot silently restore an erased plan. Changing a shortlist response does not cancel an existing plan. An author can withdraw their suggestion; either person can remove the connection and its whole shortlist. Existing plans remain separate.

Files: `shortlist-core.js` validates snapshots and independent-choice summaries; `shortlist-client.js` binds every request to the displayed Auth actor; `shortlist-view.js` connects catalog discovery, current responses, choices and privacy tools; `shortlist-runtime.js` routes the account-backed Together view. An account-backed connection link never falls through to the unsigned/local Together demo. Friends links into the new view. No remote participant is simulated in it.

`social-shortlists.sql` adds three private RLS-enabled tables with revoked raw client access and six scoped RPCs. Suggestions are immutable; per-actor responses/choices and server row locks prevent impersonation, cross-connection IDs and unilateral/duplicate plans. A caller-supplied catalog ID cannot establish source authenticity: only a matching title/link from the catalog is labeled a catalog reference; all other ideas remain participant-added/unverified. Source availability, price, rights and practical requirements still need checking.

The default gate is off. Enabling requires approved migrations in order (`social-plans.sql`, `social-plan-privacy.sql`, `social-friends.sql`, `social-shortlists.sql`) and all three `VITE_PRIVATE_PLANS_ENABLED`, `VITE_PRIVATE_FRIENDS_ENABLED`, `VITE_PRIVATE_SHORTLISTS_ENABLED` gates. This extension is outside PR #24's exact approved hosted scope. No hosted schema, real accounts, paid service or production data has been activated.

Privacy: private saves/hidden candidates stay on the browser; adding an idea sends only its explicit public title/link/ID or manually supplied idea. Shared ranking uses selected friend interests plus the current browser's private avoids; other private preferences are unknown. Anonymous analytics and merchant reporting do not receive shortlist/plan data. Own exports redact inaccessible other-person details while blocked. Removing a connection cascades its options/responses/choices; Auth deletion cascades the connection. Erasing a plan does not erase separate suggestion snapshots or intentional repeat copies; withdraw your own suggestion or remove the connection for those. Downloads cannot be recalled.

Verification commands: `npm test`, `npm run lint`, `npm run build`, `npm run test:browser`, all three `test:{plans,friends,shortlists}:configured` suites, `bash scripts/check-workspace-reporting.sh`, `npm run test:social-sql`, `npm run test:social-recovery`. SQL exercises direct denials, independently changing responses, cross-connection IDs, erasure without resurrection, fresh repeat consent, resource caps and concurrent conversion. The local friend/shortlist archive test restores exact parent/child rows including repeat references and proves Auth/blocks/existing plan data unchanged; this is not provider-level recovery.

Remaining: hosted Auth/PostgREST and real-device validation, user evidence about recommendation quality and coordination effort, maintained real local catalogs, notifications and post-experience reflection. Calendar exports and self-reports do not verify attendance. No public stranger discovery or actual participant data is enabled.

Connected builds also remove invented sample-person and simulated decision controls from generic Together. Anonymous snapshot comparisons remain available; account-backed connection links always use authoritative shared state. `social-auth-lifecycle.js` centralizes all three private screens’ Auth transitions, preserving initial invitation recovery while clearing a first-event logout or conflicting rendered actor. Unit coverage includes initial recovery event variants, same-user refresh and deferred reload outside the SDK session lock.
