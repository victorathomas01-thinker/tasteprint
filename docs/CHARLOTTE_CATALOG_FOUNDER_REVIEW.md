## How recommendations behave

- A person with no preferences gets a deterministic editorial rotation across available category/primary-interest groups. The first four eligible picks include coffee, art, nature and walking when all four are present. Input order and sponsorship flags do not change the result. This is format variety, not a prediction of compatibility or nearby distance.
- The existing interface says **“Starter picks · not personalized yet.”** No AI claim, fabricated match percentage or invented preference vector was added. Positive explicit interests continue to influence ranking; each participant’s avoids and practical requirements still apply first.
- Coffee/art/nature samples rank relevant listings first. A $0 general-admission constraint admits only the four explicit free-admission sources. Confirmed step-free filtering admits three. Requiring both admits the two listed above. No duration, user-relative distance or live availability is fabricated; requiring any of those yields no confirmed options in this pack.
- Holds are excluded. Expired field review deadlines invalidate practical facts, approval/export, the public-feed projection and checked shared-plan eligibility. In an unrestricted local draft ranking, stale metadata may still appear with the existing recheck label; the public reviewed-feed path omits it.
- The default consumer catalog remains the existing film references. Loading this draft into the local workbench never activates it in Discover or writes to a backend. The Charlotte consumer workflow was tested only through an intercepted local public-catalog fixture.

## Field evidence and maintenance

The canonical authored evidence is [`catalogs/charlotte-field-review.json`](../catalogs/charlotte-field-review.json). Every candidate has separate location, hours, admission, accessibility and visitor-restriction records with status, own-word factual summary, primary-source URLs, exact check time, expiry and recheck interval. Unknown values are null with explicit limitations. A successful HTTP response proves retrieval, not that a venue updated its page recently or that the visitor route was independently inspected.

Proposed maximum intervals: location 90 days; hours, admission and restrictions seven days; accessibility 30 days. Sensitive closure/exhibition holds use a one-day review deadline. The earliest known-field deadline becomes the listing’s `source.expires_at`; the existing 30-day overall ceiling also remains in force. Unknowns do not receive a fake verified expiry or satisfy hard requirements. These intervals are editorial policy, not source promises.

Most reviewable entries first expire around **2026-11-09**; held program/closure candidates around **2026-11-03**. Consult exact timestamps below. Recheck closure alerts before every proposed trip; do not wait for a weekly sweep. County closure notices do not explicitly state a year, so no inferred reopening date is created.

Local maintenance commands (no network, account or publication side effects):

```sh
npm run test:charlotte
node scripts/prepare-charlotte-catalog.js --due
```

After actually rechecking official facts, update the evidence, retain unknowns where necessary, advance the item revision, then regenerate explicitly:

```sh
node scripts/prepare-charlotte-catalog.js --write
npm run test:charlotte
```

`--due` prints upcoming/overdue field checks; it does not refresh dates. Consistency tests use the original review snapshot so time passing does not masquerade as a source recheck. Approval and consumer checks use their actual supplied current time. There is no scheduled job, crawler or paid service.

Use `?catalogAdmin=1` → **Bulk import and exports** → **Load Charlotte source-checked draft**. Loading only fills an empty import textarea; **Validate and import** is the separate local write. Typed text is preserved. Holds import as withdrawn. CSV now preserves status and review expiry; JSON remains the lossless interchange format. Editing a held item preserves its status unless the editor explicitly changes it. A fresh source check and exact-version review are required before approved export.

**Backend compatibility:** optional `source.expires_at` requires the accompanying additive updates to `supabase/catalog-contributors.sql` and `supabase/shortlist-requirements.sql` before any future connected use. Legacy items without expiry keep the old 30-day ceiling. No hosted schema was applied and no catalog role or gate was activated. Local disposable SQL tests cover idempotent reapplication, expiry denial at approval/publication/public feed and checked shared-plan conversion.
